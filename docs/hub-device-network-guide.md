# Hubを使って端末を接続する

Desktop 3.0.0 / LYNXの開発版向けの手順です。端末連携を実装し、同一Windows上の実Hub/Desktop画面と分離した送受信runtimeで、共通設定からの開始・参加、temp受付・有向許可・利用先選択・承認、CPU調査結果の返却を確認しました。配布済みの旧ビルドにはこの画面や通信方式が含まれません。

共通configの読込から名前・参加コードの入力なしで申請し、Hubの「許可」後にDesktopが自動接続する新しい初期設定を、実Hub/Desktop画面で確認しました。「停止」「再許可」とDesktopの自動更新、Hub経由のoMLX応答も確認済みです。

物理複数Windowsでタスク委任まで含む一連の受入と、3台再委任の受入は未完了です。受入側の対話承認、接続診断、固定IPv4・ポート、稼働中のサーバー証明書更新、成果物の書き出しには未確認の実画面操作が残ります。Hubへの接続成功だけをそれらの合格とは扱いません。確認済みの操作と残る受入条件は [Hubで管理する端末接続](design/hub-device-network.md) を参照してください。

## 初回の準備

Hubの管理者は「端末ネットワーク」で、接続するDesktopから届くこのHubのIPv4とポートを指定し、ネットワークを開始します。モデル接続とGatewayもまとめて起動します。生成に使うモデルは「登録モデル」から登録します。従来の手動サーバーを別に開始する必要はありません。

**共通設定を配る前に、Hubを動かすWindowsでファイアウォールの受信許可を確認します。** 同じPCのDesktopから接続できても、別端末からの通信が許可されているとは限りません。

1. Hubの「接続状態を診断」で、現在待ち受けているHubとモデルGatewayのIP・TCPポートを確認します。両方が別端末からの接続に使われます。
2. 許可がなければ管理者権限で受信規則を追加します。対象は実際に起動した`moyai-hub.exe`のパスと上記ポート、接続元は利用する社内LANに限定します。信頼する社内LANではPrivateプロファイルを使い、ファイアウォール全体を無効にする必要はありません。既存の許可で接続できる場合は重複追加しません。
3. 以下の手順で端末を参加させ、別端末の「Hubへの接続を診断」でTCP・TLS・モデルGatewayまで確認します。ESET等が通信を管理している環境では、接続できない場合にその製品の規則・遮断ログも確認します。

診断は受信規則を自動追加しません。Gatewayのポートが自動の場合は再起動時に変わる可能性があります。ポートを限定した規則を使う運用では「接続と証明書の詳細」で固定ポートを設定し、次回の開始後に実際の待受と一致することを確認します。アプリを別フォルダーへ展開した場合も、規則の実行ファイルのパスを見直してください。

Hubから共通設定を保存し、接続する各Desktopへ渡します。この設定に入るのはHubのURLと公開CA証明書です。A・Bとも同じファイルを使えます。秘密鍵や全端末共通の接続トークンをコピーする必要はありません。

1. Desktopで「moyAI Hub」→「端末連携」から共通設定を読み込みます。初回設定画面では「Hubの共通設定で始める」を使います。PC名と接続に使うIPv4を自動取得し、端末固有の鍵で参加申請します。名前や参加コードの入力、先行するDirectモデル設定は不要です。
2. Desktopに「承認待ち」が表示されたら、Hubの「接続端末」で申請を確認します。PC名は申告名です。接続元IP・申請日時・端末の識別情報も確認し、対象行の「許可」を押します。登録名の編集と所属グループの選択は必要に応じて行います。
3. Desktopが承認を検知し、端末証明書を取得して自動接続します。コードの受け渡しや再起動は不要です。Direct未設定の新規DesktopはHubの既定モデル割当を使います。既存のDirect設定がある場合は「モデル割当」で候補を確認・保存し、「Hubを利用」へ切り替えます。

承認前はモデルや他端末のMCPを利用できません。申請の保留中も同じ端末鍵を保持し、通常の更新・再起動で申請を再開します。端末名が同じという理由だけで別の端末と同一視しません。再インストールや端末交換の場合は新しい申請を管理者が確認します。従来の参加コード方式は互換用で、通常の初期設定には使いません。

Hubの一覧では、承認状態（承認待ち・許可・停止）と、接続・受付の申告を分けて表示します。モデルの処理状態は「モデル接続の生存確認（詳細）」、遠隔タスクの実行・停止完了はDesktopで確認します。端末の参加を許可しても、全端末へのタスク依頼が自動で有効になるわけではありません。承認時に所属グループを指定すると、そのグループに設定済みの方向付きルールを適用できます。

## モデルの変更を確認する

Desktopの「moyAI Hub」→「モデル割当」で、Main・Sideそれぞれの確認時からの変更内容を確認できます。モデルの追加・削除と、表示名・機能・Hubバージョンの確認時／現在を並べます。「この選択を確認して保存」で、そのカードの選択と比較元を一緒に保存します。Mainを保存してもSideの確認時点は変わりません。

比較元はDesktopを再起動しても残ります。以前のバージョンで保存した設定では比較元がないことを表示します。現在の一覧を確認して保存すると、次回から比較できます。変更点がないと表示されても更新番号が異なる場合は、下の変更履歴で割当方針なども確認してください。

## Win19・Win20でタスクを受け付ける

「この端末でタスクを受け付ける」で、初回に次を確認します。

- 作業場所：フォルダーに依存しない問い合わせは `temp`。開発作業は、このDesktopに登録したプロジェクトを選びます。
- 実行権限：その端末で許す操作の範囲を選びます。受付ONだけでフルアクセスにはなりません。
- モデル：通常はHubのモデル割当を使います。既存の直接接続設定を使う選択肢は詳細にあります。

確認後、受付をONにします。待受IP・ポート・TLS証明書・呼出用トークンの手入力は不要です。受付をOFFにすると新しい依頼を受け付けなくなります。受理済みの仕事を止める場合は、その仕事の停止操作を使ってください。

受付側のWindowsでも、実際の`moyai-desktop.exe`と受付TCPポートへの受信を依頼元から許可する必要があります。「保存済みの受付を診断」で待受を確認し、未許可なら対象と接続元を限定した受信規則を追加します。Hub用の規則だけで端末間のタスク通信まで許可されるわけではありません。依頼元の接続先カードでも診断してください。

`temp` は、その端末上に用意する一時作業場所です。他のすべてのフォルダーを自由に操作できるという意味ではありません。CPU使用率の問い合わせも、受入側エージェントがその端末で許された操作として調査します。Hubの登録名がWindowsコンピューター名と異なっていても、選択した受入端末上で実行します。

承認が必要な操作は受入端末の画面に表示され、依頼元にも「受入端末で承認待ち」と表示します。依頼元・公開対象・操作内容を確認し、「この操作を許可」「許可しない」「タスクを停止」を選びます。「許可しない」はその操作の拒否、「タスクを停止」は受け付けた仕事全体の停止です。遠隔タスクの承認はEscapeや画面外のクリックでは決定しません。代理承認・フルアクセスを選んだ場合も、受入端末で設定した範囲が上限になります。

複数NICやVPNで自動選択した経路が使えない場合は、受付の詳細でこのPCのIPv4とポートを指定できます。空欄は自動です。固定ポートが使用中の場合は別のポートへ黙って変更せず、変更または競合する受付の停止を案内します。

## Win00から利用する

同じHubへの登録が済んだWin00で、接続先の一覧からWin19・Win20を検索し、「この端末を利用」スイッチをONにします。端末名と公開対象を確認して選択してください。ON/OFFは保存済みの選択状態です。保存中は重複操作を止め、失敗した場合は理由と最後に確認した保存状態を表示します。Tabでスイッチに移動し、Spaceでも切り替えられます。表示される候補はHubが許可した公開対象です。Hubへの登録だけで全端末との相互接続が有効になることはありません。

「受付申告あり」はHubが受け取った公開状態です。利用ONだけでは相手への到達確認になりません。各依頼時に接続を確認するほか、端末カードの接続診断を明示的に実行できます。

依頼をチャットに入力すると、エージェントが選択済みの利用先へタスクを委任できます。作業と結果の正本は実行した端末に残ります。接続元では委任先・状態・結果を確認します。通信できなくなった場合、最後に取得した状態と現在確認できた状態を区別し、別端末で勝手にやり直しません。

## 接続できない場合の診断

Desktopでは「Hubへの接続を診断」、受付欄の「保存済みの受付を診断」、接続先カードの診断を使い分けます。保存前のIPv4・ポートを試す操作ではありません。設定を保存してから診断します。

結果はTCP、TLSと本人確認、Hubの許可、MCP等の段階ごとに表示します。「未実施」は成功を意味しません。Hub内や受入端末内の確認だけでは、別のPCから届くかを確定できません。依頼元からも診断し、失敗した段階の案内を確認してください。診断でWindowsのファイアウォールや利用先の選択を自動変更することはありません。

Hubの「接続状態を診断」はHubとGatewayの内部状態を確認します。ファイアウォールでモデル通信用の固定ポートが必要な場合は、「接続と証明書の詳細」でGatewayのポートを保存します。稼働中の変更は次回のネットワーク開始時に反映されます。現在の待受先は保存値と別に表示します。

## 成果物を確認して書き出す

終了した委任タスクの「成果物の確認と書き出し」で「成果物を確認」を押すと、その仕事が記録したファイル変更の一覧と版を取得します。追加・更新・削除記録・移動とファイル名を確認してから、「保存先を選んで書き出す」を押します。選択した場所に新しいフォルダを作成し、確認した版を書き出します。同名の既存フォルダへは上書きしません。今回の書き出しはWindowsに対応し、その他のOSでは未対応として拒否します。

元のプロジェクトへの自動適用やローカルファイルの削除は行いません。対象は、その仕事の正本に記録された変更に限ります。任意のシェル生成ファイルやプロジェクト全体の自動同期ではありません。UTF-8のファイルを最大8件、各64 KiB・合計256 KiBまで扱います。版や接続状態が変わって取得できない場合は、成果物を再確認してください。

## グループと方向付きの許可

Win00–14を「クライアント」、Win15–20を「サーバー」としてHubのグループへ登録すれば、共通の許可をまとめて設定できます。両方の役割を持つ端末は両グループに所属できます。

| 許可の例 | 意味 |
| --- | --- |
| クライアント → サーバー、直接利用を許可 | Win00–14からWin15–20を選択して利用できる |
| サーバー → サーバー、直接利用を許可 | サーバー自身の仕事で別サーバーを利用できる |
| クライアント → サーバー、再委任を許可 | クライアント由来の仕事を、受入サーバーが許された別サーバーへ委任できる |
| Win00 → Win20、直接利用を拒否する個別例外 | Win00からWin20への直接利用を外す。再委任の許可は別に判断する |

許可には公開対象の条件も付けられます。共通規則の例外が必要な場合は、端末同士を指定する個別規則を使います。Desktopの利用ONでHubの拒否を上書きすることはできません。

Win00→Win19→Win20では、Win00の元の依頼であることを引き継ぎます。Win19が自身の広い権限へ置き換える仕組みではありません。循環する経路や許された深さ・総数を超える委任は拒否します。

## 停止・再接続

遠隔作業中は同じ認可範囲のMCP接続を再利用します。毎回の接続診断やモデルによる状態確認は不要です。利用許可は操作ごとに確認し、通信に失敗した場合は次の操作で接続を作り直します。接続が切れたことを理由に同じ作業を新規作成することはありません。

エージェントには遠隔タスクをまとめて待つ機能があり、待機中はモデルを呼び出さず、結果到着や承認待ちで再開します。通常の待機上限は10分です。時間切れは作業失敗や停止を意味せず、同じjobの観測を続けられます。新しい指示を入力すると待機を早めに終了して入力を扱います。画面の進捗とMCP履歴には、依頼先の作業状態と取得済みの結果を表示します。

待機の中断と遠隔作業の停止は別の操作です。チャットの停止は、その実行が委任した作業へ停止要求を伝えます。以前の実行で委任したjobを後から待っている場合、そのチャットを停止しただけでは以前のjobは止まりません。**MCP履歴 → MCP指示**で対象の仕事を選び、**停止を要求**を押して停止確認を確かめてください。

Hubの接続端末一覧の「停止」は、その端末の新しいモデル利用やタスク依頼・受付を止めます。「再許可」で同じ登録を再開できます。実行中の仕事を終了させる操作ではなく、受理済みの仕事の状態確認・停止要求・終了通知は引き続き扱います。停止前の古い実行許可が再許可だけで復活することはありません。

受付OFF、接続先の利用OFF、Hubによる新規利用の停止、端末登録の恒久的な失効、実行中の仕事の停止は、それぞれ対象が異なります。失効は鍵漏えい等に対応する取り消せない詳細操作です。下位端末の終了を確認できるまで「停止済み」とは表示しません。Hubや実行端末へ到達できない場合は、実行端末のGUIでその仕事を確認・停止できます。

「接続を一時解除」は登録ID・公開対象・実行権限・利用先の選択を保持します。「再接続」で同じ登録に戻り、受付は手動でONにします。

Desktopの端末証明書の更新は端末ごとに自動で行います。共通なのはCAの公開信頼で、秘密鍵は各端末固有です。証明書は接続する組み合わせごとに用意しません。Hub停止・再起動後の回復と、別の物理Windows間の動作は、受入結果で確認済みの範囲を参照してください。

Hub / Gatewayのサーバー証明書は別で、有効期間30日の証明書をネットワーク開始時に生成します。期限の7日前から自動更新し、新しい接続から適用します。進行中の通信は保持します。「接続と証明書の詳細」で期限・前回の更新・失敗理由を確認でき、「証明書を今すぐ更新」で再試行できます。更新に失敗した場合も現在の有効な証明書を保持し、TLS検証を省略する接続には切り替えません。詳細は [HubのGatewayと証明書](../../moyAI-Hub/docs/gateway.md) を参照してください。

「起動時に受付を開始」を選ばない場合、再起動後は受付ONを押して開始します。トレイ格納中の継続を選ばずウィンドウを隠した場合も、再表示後は手動で受付ONにします。保存した作業場所と権限が同じなら、初回の確認を繰り返す必要はありません。

Hubは登録端末・許可・CAに加え、受理した仕事の委任関係も保存します。再起動後も現在の権限と端末資格を再確認して照会・停止を行います。通信できず停止を確認できない場合は、実行端末のGUIから確認・停止してください。未確認の仕事を自動で再実行しません。CA自体の入替を全端末へ自動展開する機能は未対応です。

完了した仕事の遠隔照会は無期限ではありません。完了した元タスクは24時間経過後、または保持する完了元タスクが128件を超える場合にHubで退役します。退役後は遠隔で再照会できませんが、端末へ保存済みの結果と取得済みの成果物は残ります。受理確認を失った古い要求も自動再実行せず、回復が必要な状態として扱います。

左メニューの **MCP履歴** で **MCP指示** と **MCP実行** を切り替え、保存済みの依頼・実行記録と結果を確認できます。詳細を選び **Markdownで保存** から `.md` に書き出せます。受付OFFやHub未接続でもローカルの履歴は残ります。指示側の表示は最後に取得した状態であり、相手の実行完了と結果取得、停止要求と停止確認を区別します。詳しくは [MCP履歴](mcp-history-guide.md) を参照してください。

従来の手動配信画面と設定・起動コマンドは廃止しました。保存済みの `mcp-publish.json`、資格情報、証明書、実行履歴は保持し、新版への更新や再起動で旧配信を再開しません。新しい受付は **moyAI Hub → 端末連携** でProject/tempと実行権限を明示して設定してください。旧read権限や共有トークンをHubのagent権限へ自動変換しません。別プロセスで動作中の旧版を停止する機能ではありません。 共通のMCP通信基盤とURL・トークンによる外部MCPへの接続設定は保持しています。
