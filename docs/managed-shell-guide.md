# 継続コマンド

開発用サーバーなど、次の操作中も動かしておくコマンドは、エージェントの
`shell_start` で開始します。通常の `shell` は親コマンドの終了時に子プロセスも
回収します。`Start-Process` 等で切り離すとサーバーが残る、という使い方ではありません。

1. `shell_start` でサーバーのコマンドを**フォアグラウンド**実行します。
2. 返却された `process_id` を保持し、別の `shell` 等で HTTP の応答を確認します。
3. `shell_status` で状態を確認し、不要になったら `shell_stop` で停止します。

`running` は OS プロセスの起動を確認した状態です。ポート待受や HTTP の正常応答は
別途確認が必要です。`success` は終了までは `null`、終了後は実際の終了コード・
timeout・取消・cleanup結果から決まります。コマンドが終了コード0でも、内部の
非終端エラーや試験の不合格がないかは、出力と検証対象そのものを確認してください。
標準出力・標準エラーは上限付きで保持し、終了後の状態確認で取得します。

## 寿命と停止

- `timeout_ms` は通常省略し、実行PCで有効な `model.request_timeout_ms` を
  実行時間の既定値・上限として継承します。必要なら正の短い時間を指定できます。
  設定の既定値は60分ですが、保存済み設定が優先されます。開始時に期限を確定し、
  AI応答・承認待ちも含めて経過します。設定変更や別PCへの引継ぎで延長しません。
  通常の `shell` は従来どおり `shell.default_timeout_ms` と `shell.max_timeout_ms`
  を使用します。
- エージェントの応答完了後、またはDesktopで別のプロジェクトを表示中でも、
  ローカルでは同じアプリケーションがプロセスを保持します。Hubの仕事では下記の
  保持指定を使います。`shell_status` の `wait_ms`
  （最大60000 ms）で、モデルを再呼出せず終了を待てます。
- 明示停止、開始元の実行の取消、実行時間上限、公開対象自体の停止や対象の失効、
  アプリケーション終了で、所有するプロセスツリーを回収します。
- ローカルの継続コマンドはDesktopのトレイ格納だけでは停止しません。
  手動MCP公開で「ウィンドウを閉じたら停止」を選んだ公開対象は、格納時にその対象の
  継続コマンドも停止します。アプリケーション終了ではすべて停止します。
  CLIの1回のコマンド実行も、CLIプロセス終了までの寿命です。
- OSへのサービス登録・アプリ再起動後の復元は行いません。同時実行は最大8件、
  状態の保持は直近64件までです。終了済みの古いIDは参照できなくなります。

Hubの仕事では、サーバーを起動する側のAIが用途に応じて指定します。

| 用途 | 指定 |
| --- | --- |
| この仕事で起動し、この仕事から別PCへ検証を依頼して待つ | `retain_for_delegation: true`。この指定だけなら仕事の完了時に停止 |
| 依頼を受けたPCで起動し、完了を返した後に依頼元PCが検証・利用する | `retain_after_turn: true` |

後者は利用者が依頼したPC間の動作確認やプレビュー用です。保持できるサーバーは
一つで、どちらの指定も元の有限期限・取消・権限失効・アプリ終了による停止を維持します。
子の完了報告だけでは稼働継続の証拠にならず、保持結果と実際の応答を確認します。
別PCの保持サーバーは共有サービスのIDで停止します。

停止を要求した直後は `stopping` の場合があります。`shell_status` で終端と
cleanup結果を確認してください。停止やtimeoutを「正常終了」と扱いません。
Hubの新規受付OFFは既存作業の停止とは異なります。既に受け付けた作業と継続コマンドは
維持されるため、必要なコマンドを明示的に停止してください。

## 権限と遠隔利用

開始時には通常の `shell` と同じコマンド審査、実行ファイルの確認、sandboxを使用します。
継続実行を理由に権限を増やしません。ユーザーが禁止した実行オプションや設定変更も
禁止のままです。これらの自然文指示の遵守と、OSによる強制的な制限は別のものです。

代理承認はプロセスの起動を確認した時点で、その起動操作について完了します。
プロセスの実行中も、次の操作はそれぞれ必要な審査を受けて進められます。
起動操作の許可を次の操作に使い回したり、拒否済みの操作を自動でやり直したりはしません。

状態確認と停止は、返却された不透明なIDと、選択workspace・依頼元の一致で制限します。
ローカルでは同じルート会話、MCPでは認証された依頼元・公開対象・元タスクが同じ
後続の委任から操作できます。別の依頼元や別の公開対象からは操作できません。
任意のOS PIDを指定して他のプロセスを止める機能ではありません。
Hubでは元タスクの権限がWinAの入力ターンに結び付くため、同じターン中の後続委任で
確認・停止します。次の入力ターンへIDだけを持ち越して操作することはできません。

Firewallの受信許可は自動変更しません。MCP通信の許可と、開発用Webサーバーへの
アクセス許可は別途確認してください。
