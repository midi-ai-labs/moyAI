# 複数端末へのエージェント委任

2026-09-06。`REC-DESKTOP-REMOTE-ORCHESTRATION-01` の採用要件と設計方針。**WinA→WinBの中間実装と同一PCでの動作確認を実施。物理2端末の中間受入は未実施**。本書の最終要件すべてが実装済みであるとは扱わない。既存の固定読み取り配信は [MCP配信](mcp-publish-foundation.md) と current code / tests を正とする。

第1〜6節はWinA＋WinB/WinC以降を含む最終要件、第7節は中間実装のcurrent owner、第8節は段階別の受入条件である。中間版は受入側のGlobal Main Direct設定を開始時にcaptureし、Bのローカル子agent・outbound MCP、対話承認、Aの親停止からの遠隔一括停止には対応しない。同一PCで委任側・受入側のcanonical sessionを分け、実GUI・実oMLXでtempへのCPU/端末名調査、結果返却、進捗表示、実shellの個別停止を確認した。物理Windows 2台の受入は未実施である。確認範囲と残条件は `project_sandbox/lynx-remote-agent-intermediate-20260906/RESULTS.md` を参照する。

## 1. 採用する利用形態

ユーザーが入力するWinAのmoyAIを、そのタスクの司令塔とする。WinAは自分の端末で作業しながら、接続を許可したWinB・WinC…の複数端末へ自然言語で作業を委任し、進捗と結果を受け取って全体の作業を進める。1対1専用の設計にしない。

端末の画面全体を同期する方式を先行条件にしない。ユーザーはWinAへ依頼し、エージェントが許可された接続先・公開対象・実行能力から作業先を選ぶ。端末指定がある依頼では指定を優先し、別端末への変更が必要なら理由を示す。毎回ユーザーが端末の画面やチャットを切り替える操作は要求しない。

WinA自身の作業は既存ローカル実行を使い、自分へのMCP配信やHub接続を必須にしない。複数端末の接続数、実行中の作業数、LLMの同時推論枠は別の制約として扱い、それぞれ上限を設ける。

| 利用例 | 期待する動作 |
| --- | --- |
| WinBのCPU使用率を教えて | WinAがWinBのtemp作業へ調査を委任。WinBのエージェントが、その端末の許可されたツールで測定し、測定対象・時刻・条件と結果を返す。WinAのCPUを測った結果で代用しない |
| WinBとWinCの状態を比較して | WinAが両端末へ個別に依頼し、結果を端末名付きで比較。片方が到達不能でも、もう片方の結果と状態を保持する |
| WinAのコードを直し、WinBでWindows試験、WinCで別環境の試験をして | WinAが編集・委任・結果統合を組み合わせる。各試験に使うcommitや成果物の版を明示し、同名フォルダに同じ内容があるとは仮定しない |
| WinBだけ止めて、WinCは続けて | WinBの対象作業だけへ停止要求を出す。WinCや同じWinBにある別の親タスクの作業を停止しない |

## 2. 責務と正本

| 対象 | 所有者 |
| --- | --- |
| ユーザーの依頼、全体の段取り、委任先の選択、結果の統合 | WinAの親タスクと既存エージェント実行 |
| 登録端末の接続先・資格情報参照・利用を許可した公開対象 | WinAの接続設定。LLMへ秘密値や任意URLを渡さず、登録IDで選択する |
| 公開プロジェクト/temp、受け入れる接続者、実行権限、実行モデル、同時実行上限 | 各実行端末の受入設定 |
| 実行中のツール、ファイル変更、承認、セッション履歴、確定した終了結果 | 実行端末の既存RunService / session / permission / storage |
| 委任の親子対応、遠隔作業への参照、最後に確認した進捗と結果 | WinAの委任記録。遠隔端末の履歴正本をローカル子セッションとして複製しない |
| モデル登録、モデルの割当・待機・revision管理 | moyAI Hub。エージェントの司令塔とは別の責務 |

当初の委任構成ではWinAがWinB・WinC…への委任を所有する。実行端末内のローカル子エージェントは既存の権限と上限に従う。追加採用した [Hub端末連携](hub-device-network.md) では、Hubが元の依頼元・直前の実行端末・次の宛先・範囲を確認した場合だけWinBからWinCへの再委任を認める。単なる接続許可の推移や、切断時の別端末への自動移送は認めない。第7節の中間実装では再委任が無効であることと、新たな採用要件を区別する。

「ユーザーが入力する端末」「作業が実行される端末」「推論モデルをホストする端末」を別々に識別する。Hub接続の有無と端末間委任の有無を独立に設定でき、モデルを共有するだけで他端末への作業権限が生じることはない。

## 3. 受入設定とtemp

固定ツールを公開する既存MCP配信と、エージェントへ作業を依頼する公開設定を区別する。既存profile・tokenの移行でエージェント実行権限を自動付与しない。

実行端末は、接続者ごとに利用できる公開プロジェクト/tempと権限を設定する。WinAのFull Access、ローカルパス、モデル設定、秘密情報をWinB/Cへそのまま継承しない。呼出側の制約は受入側の権限を狭めるために使い、広げるためには使わない。

エージェント実行用tempは、ユーザーが業務プロジェクトを選ばずに端末調査などを依頼できる対象とする。実行に必要な一時作業領域と専用セッションは受入端末が管理する。tempは現在時刻だけに限定する意味ではなく、同時に端末全体への無制限アクセスを意味しない。CPU調査で必要なコマンドも受入側の通常の権限判定を通す。

受信した依頼は、接続者・親タスク・公開対象を記録した専用実行として受理する。受信端末で人間が開いているチャットへの入力や、既存の承認の流用に置き換えない。承認が必要なら受入側で待機し、WinAにも「WinBで承認待ち」と表示する。無人運用時の代理承認等は受入側の明示設定に従う。

## 4. 作業の開始・追跡・停止

MCPを、高水準の作業委任を呼び出す通信の入口として使う。最終要件では次の意味を分離する。中間版の操作名・DTOと未対応の差分は第7節とcurrent sourceを正とする。

| 操作 | 契約 |
| --- | --- |
| 公開対象の確認 | 認証された接続者が利用可能な対象・能力・設定revision・容量を取得する |
| 作業の受理 | 自然言語の目的、必要な明示コンテキスト、親参照、要求キー、対象revisionを検証し、永続化した作業IDを短時間で返す |
| 進捗・結果の取得 | 作業IDとcursorを使い、件数・本文量を制限して更新を取得する。確定した終了理由、結果、成果物の所在と版を返す |
| 作業の停止 | 対象作業に冪等な停止要求を送る。実行端末が所属実行の終了を確認するまで停止完了にしない |

長い実行を1本のHTTP要求の生存期間へ結び付けない。MCP要求の取消やsession期限切れと、受理済み作業の停止を分離する。HTTP呼出の同時数と、長寿命の作業の同時数も区別する。

受入端末の永続ID・認証接続者の永続ID・要求キーで既受理の作業を検索し、同じ要求の再照会では同じ作業を返す。公開対象・対象revision・親参照・依頼内容は照合対象に含め、同じキーでこれらが変わった要求を拒否する。接続者のIDはMCP再接続やtoken更新で変えない。受付の永続化と実行admissionを結び付け、応答喪失、再接続、再起動後に同じ作業を新規実行しない。JSON-RPC IDやMCP session IDを、この要求キーの代わりに使わない。

実行状態と通信状態を別に保持する。実行は受付・待機・実行中・承認待ち・停止要求中・完了・失敗・中断等を扱い、到達不能時には最後に確認した状態と確認時刻を示す。ローカル通信workerの終了だけで遠隔作業の終了を確定しない。

WinAの全体停止では、その親に属する委任先へ停止を要求し、端末ごとに確認済み/未確認を示す。接続不能の作業を停止済みと表示しない。受入側の配信停止・資格情報失効・アプリ終了でも、受付停止と受理済み作業の終了を追跡し、未終了の処理を隠さない。

## 5. 複数端末を扱うGUI

- WinAに、複数接続先の名前、本人確認済みの端末、接続状態、利用可能な公開対象を一覧管理する画面を用意する。接続先JSONだけの編集にしない。名前とIPを本人証明の代わりにしない。
- WinAの親タスク内で、このPC/WinB/WinC…の各作業、公開対象、状態、進捗、結果、個別停止を確認できるようにする。遠隔詳細を開いても、WinAの入力先プロジェクトや入力中のdraftを変更しない。
- WinB/Cには、接続者、委任元、受信目的、対象、権限、状態、承認・停止への導線を表示する。受入対象の編集で実行中作業の対象を暗黙に切り替えない。
- 表示・操作対象は端末ID・作業ID・実行世代で識別し、古い応答や古い停止ボタンを別の作業へ適用しない。
- 状態は文字とアイコンを併用する。通信切断、モデル空き待ち、承認待ちを同じ「非稼働」にまとめない。

## 6. 通信・成果物の境界

複数端末の受入には、明示した待受先、暗号化された通信、相手の本人確認、接続者ごとの許可・失効を設ける。現loopback制限を外すだけでは受入完了にしない。証明書の導入・信頼設定・更新とpairingは、配布先に開発ツールを要求しないGUI/導入手順として具体化する。既存の認証付きloopback read配信を壊さず共存させる。

結果には端末と公開対象を含める。遠隔パスをWinAの同名ローカルパスとして開かない。ソースコードや成果物が必要なタスクでは、明示した版と転送対象を使う。会話履歴、秘密情報、プロジェクト全体の暗黙同期はしない。成果物のWinAへの反映はローカルの変更権限と競合確認を通す。

## 7. 中間実装の正本と残る差分

- `src/config/model.rs` の `McpConfig.servers`、`src/mcp/mod.rs`、`src/desktop/mcp_peers.rs` が複数接続先・一意ID・端末ごとのTLS信頼・資格情報を所有する。Settingsの端末追加・確認・削除から設定する。上限は32接続であり、受入側の作業枠とは別である。
- `src/mcp_publish/` はschema 3で `read_tools` と `agent` を明示的に分け、TLS待受・公開証明書生成・認証・開始/停止を所有する。旧schemaの移行は読み取り権限を維持する。agent profileは一つの公開Project/tempと受入権限を持ち、profile IDをpaired callerのprincipalとする。同じtokenを複数人に共有して個別認証したとは扱わない。
- `src/remote_agent/runtime.rs` が `delegate_task` / `task_status` / `cancel_task` を既存RunServiceへ接続する。`store.rs` とV62 migrationが専用canonical root sessionへの参照、要求キー、親参照、admissionしたturnを保存する。HTTP sessionと作業寿命を分離し、再照会だけで再実行しない。受入枠はprofileごとに1作業、process全体16作業とする。
- `src/app/run_service.rs`、`src/app/bootstrap.rs`、`src/session/`、`src/storage/` が受入端末の既存実行・権限・終端の正本である。遠隔作業は通常の人間用チャット探索から除外し、通常turnとして続行したり、受理済みのroot設定を変更したりできない。
- `src/tool/mcp_call.rs` と `assets/prompts/mcp_clients.md` がWinAのモデルへ登録端末・入力schemaを提示する。`delegate_task` の親task/turnはモデル入力を採用せず実行中のcanonical参照を付与する。WinAは通常のtool call/result履歴で受付と確定結果を保持し、専用の遠隔作業ツリー表示・親全体停止は後続とする。
- `src/app/agent_runtime.rs` の子agentは同じ端末・project・storageを前提とする。遠隔session IDをローカル子のIDへ代入せず、WinAは委任参照を持ち、B/Cは実行履歴の正本を持つ。既存のローカル並列作業は維持する。
- Desktopの受入作業欄は状態・親参照・結果preview・個別停止を表示する。`task_status` はprofileに属する `job_id` または `request_key` の片方で照会する。現段階は状態snapshotと最大64 KiBの結果であり、cursorによるイベント取得や成果物転送は未実装。Hubのmodel control planeへ作業本文や承認ownerを移さない。

受入一覧の継続監視には残差がある。現在は最近64件の一覧のため、履歴が増えた場合に稼働中の古い作業を必ず残す投影が必要になる。また、結果の開閉欄など一覧内にfocusがある間は既存の操作保護が一覧全体の表示更新を保留する。N台の監視受入までに、操作中の対象を保ちながら他の行を更新することと、稼働中の作業を履歴上限から除外することを確認する。現時点の同時多数作業のGUI合格は主張しない。

## 8. 受入条件

### 中間受入: WinA（司令塔）＋WinB（実行端末）

最初の中間受入を1対1の委任とする。WinAへの自然言語入力から、WinBの専用Project/tempセッションで実エージェントが調査・実行し、WinAが結果を受け取って返答または後続作業を行うことを確認する。GUIの画面同期を先行条件にしない。

中間では、公開設定と接続設定のGUI、受入側の明示した権限、実ツールの往復、作業IDによる状態/結果取得と個別停止、応答喪失後の同一要求の照会、既存read設定の互換性を確認する。同一PCの分離fixtureによる2役の検証と、別端末によるLAN・認証・ファイル所在の検証を区別する。

最初の実装では受入側のGlobal Main Directモデルを開始時にcaptureし、既存RunServiceで専用rootを実行する。受入側のローカル子agent・他端末への再委任は無効とする。追加の人間承認が必要な操作は明示的に拒否し、受入側で選択した代理承認/フルアクセスをWinAが変更することはできない。受入側対話承認UI、Hubによる受入モデル割当、親停止の複数端末への一括配信、成果物転送は後続の実装範囲として区別する。

受理済み記録は再照会・二重実行防止に必要なため、遠隔作業の履歴があるプロジェクトの削除は、この中間版では理由を表示して拒否する。記録の保持期限と削除後の照会契約は後続で設計する。通常のプロジェクト削除は維持する。

### 最終受入: WinA＋WinB＋WinC以降

複数接続先を持つ設計を維持し、中間受入の後にWinA＋WinB＋WinCの3役へ広げる。1対1の成功だけで次の最終条件を完了扱いにしない。

1. WinAへの1回の自然言語入力から、ローカル作業とB/Cへの委任が発生し、両方の結果を使ってWinAが続きを実行する。司令塔と受入側の双方で実エージェントのtool往復を確認する。
2. B/CのtempでそれぞれCPUを調査し、取得先・時刻・測定条件付きで結果を返す。固定の現在時刻toolやモック応答だけで、このケースを合格にしない。
3. WinAが許可された候補から実行先を選び、禁止された端末・公開対象・権限は使えない。WinAのFull Accessを指定してもB側の権限が広がらない。
4. BとCの作業が重なって進行でき、片方の待機・失敗・切断がもう片方の状態を失わせない。待受HTTP枠、作業枠、モデル枠の違いを確認する。
5. B側の承認待ち・拒否と、WinAへの表示を確認する。別接続者からの作業閲覧/停止、token失効後の新規受理を拒否する。
6. 応答喪失・重複要求・再接続・再起動で二重実行せず、同じキーの内容変更を拒否する。実行結果が不明な作業を自動でCへ再委任しない。
7. 個別停止と親全体の停止で、対象作業とその実行だけを止める。未確認の遠隔停止と、実処理の終了確認を区別する。
8. 別端末の同名パス・異なる版・成果物競合を区別し、WinAへ誤反映しない。
9. 実Tauriを直接操作し、複数端末の登録、公開設定、委任中の進捗/承認/停止、対象切替中のdraft保持、stale応答、再接続を確認する。buildや起動だけをGUI合格にしない。
10. 旧read profile・資格情報・Project/tempの互換性を保ち、再起動や移行だけではagent権限やLAN待受を有効化しない。

中間版のjob保存形式、admission transaction、認証/証明書の導入操作、Directモデル設定のcapture、個別停止は上記current ownerで実装する。成果物転送、Hubによる受入モデル割当、親全体の停止対象は後続の設計範囲とする。本書は独自plannerや巨大task graphの導入を要求しない。中間受入と最終受入はそれぞれ実施した証拠で判定する。
