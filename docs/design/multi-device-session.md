# 一つのセッションで複数PCを使う設計

2026-09-27更新。Hubプロジェクトの会話・PC利用・参加と離脱・アプリの寿命の正本。実装位置は [authority index](../../../docs/design/current-authority-index.md)、認証と導入は [onboarding](../../../docs/design/onboarding.md)、実行の永続化は [共有仕事と独立Runner](../../../docs/design/shared-work-runner.md) を参照する。

仮想WinA–WinBではLiveのPC使い分け・保持・CRUD・追加修正・停止を確認した。物理試験は委任・成果転送・再検証まで進んだが、UNC編集で不整合を検出した。最新の修正・受入状況は末尾の証跡とTODOに集約する。

## 1. 方針

導入後に利用者が送信先PC・仕事の種類・保存先を毎回設定する問題を解消する。Hubで利用範囲と各PCの作業場所を準備し、通常の入力欄へ目的を送れば、一つの会話でAIが工程と使用PCを判断する。専用フォームを詳細へ隠すだけでは、この方針を満たさない。

- 左側は一つの「プロジェクト」一覧と既存の「チャット」。Hub由来の行だけ小さな `[MCP]` 印を付ける。
- ローカルとHubで入力・添付・承認・停止・成果の基本操作を共通にする。共有範囲はプロジェクトの属性として示す。
- 操作PC／実行PCはmoyAIの利用権限であり、作るアプリのサーバー／クライアントとは別。WinAを両用途、WinBを実行専用にできる。
- AIが工程を選び、Harnessは現在の権限・端末ID・作業場所・資源・結果の対応を検証する。自然言語を固定キーワードで配送先へ変換する仕組みや別の計画エンジンを追加しない。
- 独立ローカルの会話・フォルダをHub接続だけで公開せず、Hub会話との自動移管・相互変換も行わない。
- 再参加専用の履歴復元、状況スキャン、完成度判定、探索順の固定は不要。人間が作業途中のフォルダを指定した場合も、通常agentが必要なファイルを調べる。

## 2. プロジェクト・参加・フォルダ

### 一覧と認証

現在の操作権限があるHubプロジェクトを自動表示する。Hub IDとプロジェクトIDで対応付け、同名のローカルプロジェクトを別途作成・紐づけさせない。改名は表示へ反映し、フォルダ名や内容を変更しない。通信失敗は削除と解釈せず、最後に取得した情報と接続状態を区別する。

Windowsユーザー名は申請の参考情報、端末IDと鍵は認証、PC名は変更可能な属性である。同じ人のWinAとWinBは別端末。通常利用にmoyAI独自のID/PWログインを要求しない。実行専用PCは操作用会話の閲覧権限を得ず、実行設定・受信表示・現地停止・自端末の離脱を利用する。

### 各PCの作業場所

実行PCがプロジェクトごとに既存または新規フォルダを一度登録する。異なるPCでパスが異なってよく、操作専用PCには登録を要求しない。実パスと実行許可は端末側が確認し、Hubは任意パスを許可しない。

未設定・消失した作業場所は、そのPCの当該プロジェクトだけを未準備として新規割当から外す。以前の版で自動生成した場所にも適用し、Runner全体の起動や再選択を妨げない。他の準備済みプロジェクト・PCは利用できる。登録先の新規設定・変更は、このPCの全仕事・保持アプリ・未終了processの停止確認後に行う。Desktopは既存Runnerの稼働事実から可否を投影し、停止が必要な間は理由表示と選択の無効化を行う。操作エラーは状態pollで消さず、次の操作または接続変更まで保持する。ファイルの自動移動・削除・全体同期、消失フォルダの無断再作成は行わない。

PCの「フォルダーの作成先」は新規作成用の保存先、プロジェクトの「作業フォルダー」は実行対象の場所として区別する。作成先の変更で既存の対応付けを移動せず、消失・変更時は対象プロジェクトからの再選択を案内する。

### 参加の変更

| 操作 | 挙動 |
| --- | --- |
| Hubで作成・PC追加 | 操作PCの一覧へ表示。実行PCは今回の参加に対するフォルダを設定 |
| Hubで改名 | 操作PCの表示へ反映。フォルダは変更しない |
| Desktopで「プロジェクトから離脱」 | このPCの操作・実行の両用途を解除。操作PCは一覧から、実行専用PCは実行設定から操作 |
| HubでKick | 対象PCの当該プロジェクト参加だけを解除。Hub端末登録と他プロジェクトは保持 |
| 操作用途だけ解除 | 会話へのアクセスを解除。残る実行用途・受信表示は維持 |
| 実行用途だけ解除 | 新規割当を止め、当該実行と保持アプリを停止へ進める。残る操作用途は維持 |
| Hubでプロジェクト削除 | 全参加PCの通常利用を解除し、共有会話・成果参照を論理削除。対象の実行を清算 |

離脱・除外・削除は、停止要求の受理と実停止確認を分ける。未確認の仕事を一覧から隠すだけで放置せず、実行・保持アプリと資源は確認まで追跡する。端末上のフォルダ・生成ファイル・取得済みコピー、他プロジェクトと他PCの参加は削除しない。

Desktopの離脱要求はHubで確定するまで受付待ちとして保存し、そのPCから当該プロジェクトへの新規依頼を止める。Hub側の除外はオフラインPCの再接続時に反映する。旧権限の遅延要求・承認・応答で資格や実行を復活させない。旧Hubが失われた場合の接続リセットは、プロジェクト離脱とは別のローカル復旧操作である。

### 再参加は新規参加

有効なHub端末登録は再利用できるが、プロジェクト参加とフォルダ設定は新しく作る。同じ実フォルダを改めて選んでもよい。旧session・draft・未確定受付・承認・checkpoint・保持アプリを新参加へ復元・移管しない。鍵が変わった端末はHub登録から行い、名前一致で旧資格を引き継がない。

「History不要」は再参加専用の引継ぎ機構が不要という意味である。共有会話や二重実行防止・停止照合の台帳は保持し、再参加後も現在の権限で共有会話を閲覧できる。旧仕事は自動再開せず、停止未確認の資源は再参加だけで解放しない。一時切断・通常再起動では参加を失わず、元の要求と実行状態を照合する。

## 3. 会話とPCの判断

利用者に見える単位は一つの会話。その下の根仕事、子仕事、試行、保持アプリを会話IDへ結び付ける。Hubが会話の順序・共有範囲・親子関係・取消を、Runnerの既存storageが実行履歴を所有し、Desktopに第三の編集可能な履歴を作らない。

新規入力の初期進行役はHubが許可先から決める。現在の操作PCが実行可能なら優先し、同条件は環境ID順で選ぶ。継続は元の会話の実行先と状態を照合する。これは最初の推論を置く処理であり、プロンプトに従って工程ごとのPCを選ぶAIの判断とは別である。未完了仕事を不在だけで別PCへ再配置しない。

AIへ渡す候補は会話のプロジェクトと実行許可で限定し、端末ID・PC名・環境・機能の宣言／確認結果・稼働状況を区別する。PC名やソフトの説明は情報であり、資格やシステム指示にはしない。実ソフトの動作・ライセンスは対象PCで確認する。「WinBをホスト」等の明示条件はAIが理解し、利用不能なら理由を返す。Harnessがモデルの判断品質まで保証する意味ではない。

### プロジェクト概要と委任の文脈

Hubのプロジェクト編集に自然言語の概要を一つ保存する。既存の管理者認証・管理revisionを使い、前後の空白だけを除いて本文の改行を保持する。上限はUTF-8で8 KiB、未設定・旧データは空。省略した旧管理要求では既存概要を消さない。

Hubは根依頼の受付時に、プロジェクトID・名前・概要・採用revision・全体の依頼・依頼元PCを根仕事へ一度保存する。子と再委任先、checkpointからの親再開は根仕事の同じsnapshotを参照する。同じ会話の次の依頼は新しいsnapshotを持つ。過去の仕事へ現在の概要を遡及して付けない。

AssignmentからSharedRunContextへ渡し、既存WorldStateを毎step組み直す際に説明情報として描画する。現在の実行環境IDは各Assignmentから取り、依頼元PCとは別に示す。概要はモデルへのsystem指示や権限ではない。現在の参加・認可・環境候補・停止は既存のHub/Runner境界で照合し、snapshotに固定しない。Hubを使わない会話にはこの節を追加しない。

全体の設計・配置・分割・統合・最終確認は通常の親agentが判断する。shared_delegateの既存promptに、全体目標、委任時点の工程、担当範囲と制約、完了条件、返す結果を短く示す。環境事実を毎回自由文へ転記させず、利用者にこの書式の入力を要求しない。独自planner・必須Planning工程・端末名の固定配送は追加しない。子の再委任可否は既存の契約に従う。

共有agentは現在のregistryを通じてPC照会、子への依頼、選択ファイルの転送、成果取得、停止を行う。子待ちでは保存されたcheckpointから再開し、状態確認だけのモデル呼出しを繰り返さない。CLI/TUIから同じagentを使っても認可・結果・停止を迂回できない。Side Chatには実行toolを追加しない。

### 実行途中の記録

操作PCには、現在実行中の親または子のPC名と、確定した応答・操作・成否を同じ会話内に表示する。原本はRunnerの既存canonical historyであり、現在のsession/turnの公開部分だけを最大12件・64KiBの直近抜粋として送る。内部推論・provider diagnostics・入力prompt・画像・tool metadataは送らない。更新時刻はHubでの初回受信時刻であり、モデルの生成中を示す時計ではない。

Hubは現在のattempt・世代・実行主体・閲覧権限を検証し、表示用cacheをattemptごとに最新1件だけ持つ。途中記録は完了・資源返却・期限延長の根拠にせず、終端ではactivityを外して保存済みarchiveの実行記録へ切り替える。遅延応答で終了表示や別参加の会話を戻さない。

配送は既存tick/report/pollを用いる。Runner journalは未ACK packetを最大1件保持して同内容を再送し、ACKまたは終端で除去する。表示失敗で仕事を再実行せず、新しいtimerや生成期限は設けない。既存control HTTPの最大10秒の待機中は次tickの停止観測が遅れ得るが、副作用直前の権限・取消照合は維持する。厳密な配送契約は [共有仕事と独立Runner](../../../docs/design/shared-work-runner.md) を参照する。
### 会話の作成・変更・削除

操作権限のあるPC間で会話の表示・更新を共有する。追加指示は元の依頼元本人とPCに限定し、別PCは独立した会話を開始する。子仕事や再試行を独立チャットに増やさず、タイトル・時刻の類似で別会話を統合しない。同時送信や古い操作は会話版・参加世代で拒否し、入力を保持する。新しい次ターン予約は追加しない。

### 承認を判断するPC

承認の操作主体は、その発言を送った操作PCである。WinAから依頼しWinBが実行する場合、WinBの代理承認から人の確認へ移った操作もWinAの同じ会話へ表示する。実行専用PCには受信状況と現地停止だけを提供し、承認のために操作権限を追加させない。同じ利用者に紐付く別PCや別の管理者へ、通常の承認権限を自動で移さない。

Hubは子を含む現在の承認依頼を、操作ID・実行試行・担当世代・送信元PCの参加世代に結び付ける。会話の選択は親のまま、対象PC・仕事・操作内容を示し、判断はその正確な子の操作へ送る。切断・期限切れ・取消・離脱を許可と扱わず、回答の受取と副作用直前にも資格を再検証する。Guardianの明示的な拒否を人の承認で上書きする経路は追加しない。

承認の15分期限切れは拒否や仕事停止ではなく、同じ操作の待機として扱う。依頼元PCで「操作を再確認」を選ぶと既存brokerの待機を新しい承認IDで提示し直す。古い回答は実行許可にならず、自動再発行で承認履歴を増やさない。

共有仕事の人の「許可しない」「仕事を停止」は、現在の依頼とその子仕事を取消へ進める。子の失敗をきっかけに親が別経路で自動続行せず、次の利用者の指示を待つ。当該turnの保持アプリも停止へ進め、実終了の確認まで資源を保持する。否定回答の再送は新しいturnへ作用せず、拒否・停止の記録は元の会話へ残す。

担当交代とその承認例外を廃止する。通常の追加指示・発言改訂・承認・停止は保存された依頼元本人と端末に固定し、子・再委任・親再開でも維持する。別操作PCは自分の独立した会話を開始する。共有閲覧・名称編集・清算済み履歴削除のrole権限は維持し、実行停止を伴う削除は依頼元を照合する。管理上の取消・実停止清算と実行PCの緊急停止は別経路で保持する。V25では旧pendingを不活性化し、確定済み交代scopeに未清算job/attempt/serviceが残る場合は移行前に拒否する。履歴は残し、旧交代先から通常継続できる経路は閉じる。

同じプロジェクトIDでも参加世代が変われば新規参加として扱う。離脱確認は表示時の参加世代をcommandに含め、最新世代へ読み替えない。下書きの識別にも参加世代を含め、poll間の離脱・再参加を検出した場合も、旧会話・入力参照・承認・画面操作の対象を破棄し、新参加へ転用しない。選択世代の変更後に届いた旧要求の応答も画面へ採用しない。

会話の削除は他の操作PCにも及ぶことを表示し、対象の仕事・保持アプリの停止確認後に完了する。実ファイルは削除しない。

通常チャットとHub会話の**最新の送信済み発言だけ**を編集・再送できる。実行中なら先に停止し、Hub会話では保持アプリも終了確認してから編集する。元の履歴を残し、修正後へ古い応答を混ぜない。ローカルは新しい分岐、Hubは同じ会話内の改訂として表示する。編集対象は本文とし、元のローカル画像の保存済み内容・Hubの添付参照をそのまま再送する。元ファイルを読み直したり、添付を追加・削除・差し替えたりしない。保存内容の破損やHub添付の削除、権限の喪失があれば理由付きで拒否し、新しい依頼を案内する。編集・再送は実ファイル、DB、アプリの巻戻しではない。

受付結果が不明な送信は元の内容と要求IDで照合する。認証sessionの再発行と受付receiptは分離し、別会話・別利用者へ未確定要求を移さない。

## 4. 保持アプリ・排他・停止

一回のコマンド、別PCでの検証中に維持するサーバー、turn後も利用するプレビューの寿命を分ける。AIが用途に応じて既存managed shellの保持指定を行い、Runnerが会話・試行・正確な管理ハンドル・資源をHubへ結び付ける。PIDやポート名から所有者を推測しない。

セッション・初期待機列・子待ち・親再開に暗黙の総時間制限を設けない。健全な72時間超の作業と資源待ちを経過時間だけで終了させない。`shell_start` は既定で総時間制限を持たず、LLMの応答待ち時間とは独立する。既存APIで明示された正の `timeout_ms` だけは開始時に確定する旧互換の期限として守る。通常の `shell` とprovider接続の時間設定は変更しない。試験用サーバーは検証後に止め、利用者が要求したプレビューは明示停止・権限失効・Runner終了・Hub制御喪失まで保持する。

既定では一つのPCを共通資源枠とし、プロジェクトや設定を増やして容量を増やさない。同じ会話が同じPCへ戻る工程は有効な保持ID・workspace・世代を照合して元の資源へ参加する。無制限な再入や別会話への貸出しはしない。ローカルCLI/TUI/Desktopの競合も同じ受付境界で扱う。管理外ソフト・OS全体の入力・ライセンスまでロックできるとは扱わない。

| 操作・事象 | 範囲 |
| --- | --- |
| 通常の停止 | 現在のAI作業と子仕事へ取消要求。確定済みの利用継続用プレビューは別に表示 |
| アプリ個別停止 | 正確な保持IDのアプリを停止。依存する工程に停止理由を返す |
| 会話の実行をすべて停止 | その会話の保持アプリも対象。古い要求が後続turnを止めないよう世代を固定 |
| 離脱・Kick・削除・実行権限失効 | 該当範囲の新規操作を拒否し、仕事・保持アプリを停止へ進める |
| 受信PCの現地停止 | そのPCの正確な実行を停止できる。業務の閲覧・承認権限は増えない |
| Hub制御喪失・Runner再起動 | 不明を成功・空きにしない。Hub制御喪失ではworkerと保持アプリを停止へ進め、実停止と報告受理まで枠を保持。Runner再起動後の自動再実行は行わない |

実停止とHubへの報告を確認して資源を解放する。×によるトレイ格納は仕事停止の操作ではない。実行PCのDesktopの明示「終了」は接続中Runnerの仕事・保持アプリを正常停止し、実プロセス終了を待つ。Windowsサインアウト後の継続、本番サーバーの無期限運用、モデルprovider自体の管理は保証しない。

## 5. 受信表示と成果

Runnerの観測をRustが端末全体の状態として投影する。開いている会話によらず使用中・承認待ち・停止中・不明・保持アプリと停止入口を示す。実行枠を使う間は競合するローカル送信を禁止し、下書き・閲覧・切替・停止は使える。通信失敗だけで表示を消さず、終了確認後に解除する。UIだけでなくcommand境界でも対象を検証する。

仕事詳細の閲覧権限がない場合は「詳細を表示できない仕事」とする。受信監視のために操作PCへの登録を要求しない。Rustが保存／実効状態を、TypeScriptがdraft・focus・selection・scrollを所有し、状態更新で入力中DOMを置換しない。

入力と成果は、AIが選んだファイルを既存Hub保管経路で固定コピーし、会話・仕事・入力版・実行PC・ハッシュを照合する。フォルダ全体の同期や、同名パスを同一workspaceとみなす処理は行わない。通常の成果共有を追加依頼の必須手順にせず、選択された成果を会話へ表示する。

操作専用PCは実行フォルダなしで成果を閲覧し、通常の保存操作で取得できる。既存ファイルへの取込みは基準版と現在内容を検証し、不一致を上書き成功にしない。Hubの保存コピーは端末の現在ファイルと同一視せず、離脱用の自動回収や成果所在追跡を追加しない。

生成、保存、共有、起動、別PCからの到達は別の結果として扱う。Hubに接続できてもFlaskのポートへ到達できるとは限らない。アプリの待受・依存ソフト・FWは実接続と通常の承認で確認し、Hub向けFW規則を任意アプリへ拡張しない。モデルの誤ったコードとHarnessの配送・保存・状態不整合を区別する。

## 6. 互換性と受入

更新では既存の端末ID・鍵・Hub CA・モデル設定・実行許可・参加を保持する。released migrationは書き換えず、既存job・checkpoint・監査をforward migrationで維持する。有効な旧checkpointの復帰は正確な仕事の継続であり、離脱後の新参加へ引き継ぐ処理ではない。

途中記録はAssignmentの `supports_progress_reports` がtrueのHubだけへ送る。欠落時はfalseとし、旧Hubとの組合せでは区切りごとのarchive表示を維持する。旧Runnerは追加fieldを無視して既存動作を続ける。

旧Runnerには非対応の保持要求等を渡さず、必要な更新を案内する。旧ローカルorigin仕事と旧個別MCPの保存済み仕事は照会・停止・清算・成果取得を維持し、新規導線へ戻さない。互換境界は [旧端末間委任](remote-agent-delegation.md) を参照する。
